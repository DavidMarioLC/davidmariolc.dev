At Mercado Lento, a fictional store, login was solved in two lines:

```ts title="src/auth/login.ts"
const token = jwt.sign({ sub: user.id }, process.env.JWT_SECRET, {
  expiresIn: "15m",
});
localStorage.setItem("access_token", token);
```

It works on the first try. A week later someone asks how many people are logged in right now, you open the database looking for the sessions table, and there isn't one. So where is the session?

## The sessions table that doesn't exist

Nobody deleted it: it was never created. If you expected to find it, that's fair — in a classic session system login inserts a row, the cookie holds its identifier, and that row *is* the session.

With JWT (JSON Web Token: a signed object the client stores and resends on every request) there is no row to look up. That `sub` in the snippet — the claim that says who the token belongs to — travels inside the token itself, and the server reads it from there instead of querying for it. The session didn't disappear: it's split across pieces that barely talk to each other, and knowing which one holds what is pretty much the whole design.

## Your session lives in three places at once

Think about how a hotel works.

At the front desk you show ID once and get a key card encoded with your room and an expiry date. From then on, every lock on the floor decides on its own: it doesn't call the front desk, it has no connection, it only knows how to check that the code is legitimate and that the date hasn't passed. And your reservation stays in the front desk's computer, which is what lets you get a fresh card tomorrow without showing ID again.

Three pieces, three different things:

| Hotel piece | What it holds | Where it lives |
| :--- | :--- | :--- |
| The key card | who you are and until when | in your pocket — the client |
| The lock | how to verify a card | in every service that validates |
| The reservation | your right to another card | in a table on the server |

None of the three knows what the other two are doing. That's what the pattern buys you, and also everything that gets awkward later.

### The front desk signs the card and writes nothing down

Login is the only moment the password travels. The server compares it with the stored hash, builds a payload with who you are (the `sub` claim) and how long it's good for (the `exp` claim, the expiry date the library writes for you when you pass `expiresIn`), seals it with its secret and returns the token:

<ConceptAnimation id="jwt-login" />

The step that defines the architecture is the last one: the server signs and keeps no copy. That's why there's no sessions table to query — and why, when the time comes to end the session, there will be nothing to delete either.

### Every lock decides on its own

On every request the server does three things with the incoming token. It splits it at the dots into its three parts — header, payload and signature — recomputes the signature with its secret and compares it against the one the token carries, and checks whether the payload's `exp` has passed. If anything fails, 401:

<ConceptAnimation id="jwt-validation" />

What matters is what **didn't** happen: a database query. That's the property you're paying for with everything else — any service holding the secret can validate without coordinating with whoever issued the token, which is why the pattern fits when there are many verifiers and a single issuer.

<Callout type="warning" title="The payload is not encrypted">
  The first two parts of the token are `base64url`, not cryptography. The
  signature guarantees nobody **modified** the payload, not that nobody
  **reads** it: whoever holds the token can decode the whole thing. It's the
  hotel key card with the room number printed on the front. Never put an
  internal email address, an ID number, or anything you wouldn't publish in
  there.
</Callout>

## From a lone token to an access token + refresh token pair

Go back to the hook's code. It issues a token with a fifteen-minute lifetime and makes no plan for who renews it, so exactly fifteen minutes later the API starts returning 401 and the user gets dropped in the middle of a form. Nobody is going to retype their password every quarter hour, and stretching `expiresIn` to a week just moves the problem: a stolen card would open the door for seven days.

The way out is to split the two roles that were crammed into one token. The **access token** is the day's key card: short, stateless, shown at every door. The **refresh token** is the reservation at the front desk: long-lived, single-use, stored in a server table and — on the client side — in an `httpOnly` cookie, which the page's JavaScript cannot read.

<ConceptAnimation id="jwt-refresh" />

There's the asymmetry the whole pattern is organized around: the access token is stored nowhere, which is why it validates without asking anyone; the refresh token is stored, which is why every use costs a read and why it can be invalidated.

At login that means issuing two things instead of one:

```ts title="src/auth/login.ts"
const token = jwt.sign({ sub: user.id }, process.env.JWT_SECRET, { // [!code --]
  expiresIn: "15m", // [!code --]
}); // [!code --]
localStorage.setItem("access_token", token); // [!code --]
const { accessToken, refreshToken } = issuePair(user.id); // [!code ++]
```

`issuePair` signs the access token just like before and additionally generates an opaque refresh token: a random string with no claims inside, which the server doesn't verify but looks up. Each one is stored in a different place, and that split is half of the scheme's security:

```ts title="src/auth/login.ts"
await db.refreshTokens.save({ hash: sha256(refreshToken), userId: user.id });

res.cookie("refresh_token", refreshToken, {
  httpOnly: true,
  secure: true,
  sameSite: "lax",
});
res.json({ accessToken });
```

The table stores the hash of the refresh token rather than the token, the same way you'd treat a password: whoever walks off with a database dump doesn't walk off with sessions. And the access token comes back in the response body so the client can keep it in JavaScript memory instead of `localStorage` as in the hook. The practical difference is the page reload: what's in `localStorage` is still there tomorrow, so an attacker only has to land once; what's in memory forces them to be running at that exact moment.

## What checkout takes with it

Logging out moves two of the three pieces. The client drops its access token and the server deletes the refresh token row, so the session can no longer be renewed. The third piece doesn't move: any loose copy of the access token — in a log, in a proxy — still carries a correct signature and an `exp` that hasn't arrived.

<ConceptAnimation id="jwt-logout" />

It's hotel checkout. Your reservation disappears from the front desk's computer, and the card somebody copied keeps opening the door until its date, because the lock never finds out about anything. With fifteen minutes of `expiresIn` that window lasts fifteen minutes at most; closing it completely means giving state back to validation — putting a list of burned cards back into every lock — and that's what the next post in this series is about.

## Who can issue an admin token?

Mercado Lento grows. There are now four services validating tokens — orders, payments, catalog and notifications — and a single one issuing them, the auth service. All five share the same `process.env.JWT_SECRET`, because they sign with HS256, the shared-secret algorithm. How many of those services can issue a token that says `role: "admin"`?

<Challenge summary="See the real count">
  All five.

  With HS256 the secret that verifies is exactly the secret that signs, so
  anyone able to check a token is able to forge one. The notifications service,
  which only needed to know who to email, can sign itself an admin token and
  walk into payments with it.

  That's why HS256 versus RS256 isn't a decision about how much security you
  want, but about the shape of your system: RS256 signs with a private key and
  verifies with the public one, so you can hand the public key to all four
  verifiers without handing out the ability to issue.
</Challenge>

## The details that bite in production

**Keys rotate, and that's what `kid` is for.** The day you change the key you sign with, every already-issued token stops verifying at once. The token's header carries a `kid` (key id) saying which key signed it, and the verifier picks the right one from a key set — typically published at a JWKS endpoint that services cache. With that, two keys coexist during the transition and no user notices a thing.

**`iss` and `aud` exist because a valid token can be the wrong token.** The `iss` (issuer) claim says who issued it and `aud` (audience) says which service it's for. Without checking `aud`, a token a user legitimately obtained for the catalog service also gets into payments, because the signature checks out just the same. Verifying the signature is only half the job: the other half is verifying the token was addressed to you.

**`exp` is compared against each verifier's clock.** Five machines have five clocks, and a few seconds of drift are enough for one of them to reject tokens the others accept, with an intermittent 401 nobody can reproduce. Serious libraries accept a few seconds of tolerance (`clockTolerance`); the real fix is NTP on every machine.

**Validating at the gateway or in every service.** Validating once at the edge is convenient and leaves internal services trusting a header; validating in each service costs a few microseconds per request and removes the assumption that nobody reaches you from inside the network. If you pick the first, make it a written decision rather than an accident.

**When JWT isn't the answer.** The pattern shines with several verifiers and one issuer, or when the verifier can't talk to the issuer. For a monolith with its database right there, a classic session is simpler, revokes instantly, and never makes you explain to anyone where the session lives.

## Three rules worth remembering

- **Your session lives in three places**: the access token on the client, the ability to verify it in every service, and the refresh token in a table. Every problem in this pattern makes sense once you ask which of the three found out about the change.
- **The access token is stored nowhere**, and that single decision gives you query-free validation and takes revocation away from you.
- **The refresh token is the only stateful piece**, so it's the only one you can really delete: anything you want to be able to cut off has to lean on it.

Open your project's login and answer three questions: which tokens you issue, where each one ends up stored, and which services share the secret. If the answer to the third is "all of them", you already know how many of them can sign themselves an admin token.
