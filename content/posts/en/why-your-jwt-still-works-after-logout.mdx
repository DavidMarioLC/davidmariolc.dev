In the dashboard of Slow Market, a made-up shop, the log out button does this:

```ts title="src/auth/logout.ts"
export function logout() {
  localStorage.removeItem("access_token");
  router.push("/login");
}
```

Before clicking it you copied the token into a file. Now, with the session "closed", you paste it into a `curl` against the API. What comes back?

## The surprise: the token never heard about the logout

Two hundred both times. If you expected a 401, you are in good company: that is what any classic session system does, where logging out deletes a row and the next request finds nothing.

With a JWT (JSON Web Token: a signed object the client stores and resends on every request) there is no row to delete. The server never stored your token. And you cannot delete what you never held.

## The festival wristband

There are two ways to let people into a venue.

The first is the **list**. There is a tablet at the gate with everyone's name, and security looks yours up each time you walk in. If you get thrown out, your name is deleted and the next attempt finds nothing. That is a classic session: the state lives on the server, and the cookie is just a number pointing at it.

The second is the **wristband**. You show ID once at the box office, they put a band on you with a seal nobody can forge, and from then on nobody looks anything up: the person at the gate checks the seal, checks that the printed date has not passed, and waves you through. It is fast, it works across twenty gates, and none of them needs to talk to the box office.

That is a JWT. And the trade-off is exactly the one that just bit you: **if you get thrown out of the festival, the band on your wrist is still valid**. Nothing in the basic design lets anyone deactivate it remotely, because it is not on any list: it just expires on its own. Later in the post we will see what adding that capability costs.

Every awkward part of the pattern comes from there. Let's walk the whole thing with that picture in mind.

### How the band goes on

Login is the only moment the password travels. The server compares it against the hash it stored, builds a payload with who you are (the `sub` claim) and how long it is good for (the `exp` claim), seals it with its secret, and hands the token back:

<ConceptAnimation id="jwt-login" />

The thing to hold on to is the last step: the server signs the token and lets it go without keeping a copy. That decision — writing nothing down — is what lets it validate later without a lookup, and what stops it from revoking.

### How the gate reads it

On every request the server does three things with the token that arrives. It splits it at the dots into its three segments — header, payload, signature — recomputes the signature with its secret and compares it against the one that came in, and checks whether the payload's `exp` has passed. If anything fails, 401:

<ConceptAnimation id="jwt-validation" />

Notice what there was **not**: a database query. A server that validates this way takes any amount of traffic and replicates without coordination, because each replica only needs the secret.

<Callout type="warning" title="The payload is not encrypted">
  The first two parts of a JWT are `base64url`, not cryptography. Copy the
  middle segment (what sits between the first and second dot), swap `-` for
  `+` and `_` for `/`, and run it through `atob()`: there is your payload in
  the clear. The signature guarantees nobody **changed** it, not that nobody
  **reads** it. Never put an internal email, an ID number, or anything you
  would not publish in there.
</Callout>

## From the naive version to a pair of tokens

Signing and verifying are five lines. This is the naive version, the one nearly everyone writes first:

```ts title="src/auth/tokens.ts"
export function issue(userId: string) {
  return jwt.sign({ sub: userId }, process.env.JWT_SECRET);
}
```

With no expiry date the wristband lasts forever. A token leaked today still opens the gate next year. That date is the `exp` claim, and the library writes it for you if you pass `expiresIn`:

```ts title="src/auth/tokens.ts"
return jwt.sign({ sub: userId }, process.env.JWT_SECRET); // [!code --]
return jwt.sign({ sub: userId }, process.env.JWT_SECRET, { // [!code ++]
  expiresIn: "15m", // [!code ++]
}); // [!code ++]
```

Which surfaces the obvious problem: fifteen minutes. Nobody is going to retype their password four times an hour.

### Which is why there are two tokens

The fix is to separate the two jobs you had merged. The **access token** is today's wristband: short, stateless, shown at every gate. The **refresh token** is the festival pass: long-lived, single-use, stored in a table on the server and — on the client side — in an `httpOnly` cookie the page's JavaScript cannot read. It is what gets you tomorrow's wristband without going back to the box office with your ID.

<ConceptAnimation id="jwt-refresh" />

Every login opens a **family**: the refresh token you were handed, the one that comes out of redeeming it, and so on. They all share a `familyId`, and that is the unit you revoke — not the single token, and not the whole user, who may have other legitimate sessions open.

In code, the refresh token is the opposite of the access token: it gets stored, looked up, and marked.

```ts title="src/auth/refresh.ts"
const stored = await db.refreshTokens.findByHash(sha256(incoming));

if (!stored) {
  throw new AuthError("invalid refresh token");
}

if (stored.usedAt) {
  await db.refreshTokens.revokeFamily(stored.familyId);
  throw new AuthError("refresh token reused");
}

await db.refreshTokens.markUsed(stored.id);
return issuePair(stored.userId, stored.familyId);
```

That `stored.usedAt` is the part people skip. If a refresh token that was already redeemed shows up again, either the client has a bug or somebody is using a stolen copy. In both cases the correct answer is the same: tear down the whole token family and force a login.

### The logout: what it cuts and what it does not

With both pieces on the table, it is clear why the `curl` at the top returned 200. Logging out moves three things: the client deletes its copy of the access token, the server deletes the refresh token's row, and any other copy of the access token — in a log, in a proxy, in somebody's clipboard — still carries a correct signature and an `exp` that has not arrived.

<ConceptAnimation id="jwt-logout" />

Which is exactly what was wrong with the `logout()` at the top: it only did the first of the three.

```ts title="src/auth/logout.ts"
export function logout() { // [!code --]
export async function logout() { // [!code ++]
  await api.post("/auth/logout"); // [!code ++]
  localStorage.removeItem("access_token");
  router.push("/login");
}
```

The `removeItem` is still needed, but it is the secondary half. What actually ends the session is that `POST`: it deletes the refresh token's row on the server. Without it, the client forgets its token and the server stays willing to renew it for whoever asks.

The honest summary: **logout is complete for the refresh token and partial for the access token**. You cut the ability to renew the session immediately, and you leave a window the size of whatever life the access token has left. With a fifteen-minute `expiresIn`, that window is fifteen minutes at worst.

That window can be closed. You store the `jti` — the unique id every token carries — of the ones you revoke, and the API checks that list before serving each request: it is putting a tablet back at the gate, holding a much shorter list than the original, just the burned wristbands. It costs precisely what JWT had saved you, which is why I unpack it at the end of the post.

<Callout type="tip" title="Pick `expiresIn` by looking at that window">
  Do not pick it for convenience: it is literally how long an already-closed
  session survives. Fifteen minutes is reasonable for an internal dashboard.
  For anything that moves money, the question is not "how long should the token
  last" but "how long can you go without being able to cut someone off".
</Callout>

## When do they stop being an admin?

The team puts the role in the payload so they do not have to look it up on every request:

```ts title="src/auth/tokens.ts"
jwt.sign({ sub: userId, role: "admin" }, process.env.JWT_SECRET, {
  expiresIn: "15m",
});
```

At 10:00 you strip someone's admin role in the database. Their token was issued at 9:58. When do they stop being an admin?

<Challenge summary="See what actually happens">
  At 10:13, not at 10:00.

  The server never reads the roles table: it reads `role` from the payload, and
  that payload froze the moment it was signed. Changing the database does not
  change a wristband that is already printed. For thirteen minutes that person
  keeps walking in as an administrator with a perfectly valid token.

  It is the logout problem wearing different clothes: **everything you put in
  the payload is a copy with an expiry date, not a lookup**. It works for what
  rarely changes (the `sub`, the tenant) and is a trap for anything someone can
  change by decision, like permissions or account status.
</Challenge>

## The details that bite in production

**`alg: none` and algorithm confusion.** The header — the token's first segment — declares which algorithm signed it, and it was chosen by whoever sent it to you. The spec still allows `"alg": "none"` today: an unsigned token that a careless library happily accepts. The modern variant is worse: if your server signs with RS256 (private and public key) and someone resends the token claiming `HS256`, a naive implementation will verify the HMAC using **the public key** — which is public — as the secret. This is why serious libraries take the expected algorithm as a required argument to `verify`, and why you must never read it from the token itself.

**HS256 versus RS256 is not a security decision, it is a topology one.** HS256 uses a single shared secret: whoever can verify can also sign. That is fine while the issuer and the verifier are the same service. The moment five services verify tokens, HS256 means five services able to mint admin tokens. RS256 signs with the private key and verifies with the public one, so you can hand the public key out everywhere without handing out the power to issue.

**Where to keep the access token.** `localStorage` is convenient and readable by any script that sneaks onto your page; an `httpOnly` cookie is invisible to JavaScript but rides along on every request, which opens the CSRF door unless you pair it with `SameSite=Lax` and an origin check. There is no free option. The current consensus for a web app: refresh token in an `httpOnly` `Secure` `SameSite` cookie, access token in JavaScript memory — not `localStorage`, not a cookie. Not because XSS cannot read a variable in memory, which it can, but because it does not survive a reload: the attacker has to be running at that moment instead of collecting what was left lying around. It is lost on reload, and the refresh token puts it back.

**What a denylist actually costs.** Storing the `jti` of everything revoked is cheaper than it sounds: only tokens revoked **before** expiring go in, and each entry deletes itself once its `exp` passes. With a fifteen-minute lifetime, a mid-sized system's denylist fits comfortably in memory. What does change is the property you were bragging about: you are back to one read per request and a shared point that can go down. If you accept that, it is worth asking out loud whether you wanted opaque sessions in Redis all along — instant revocation, an id everywhere, and a token that leaks nothing because it says nothing.

**When JWT is not the answer.** The pattern shines when several services verify and one issues, or when the verifier cannot talk to the issuer. For a monolith with its database next door, a classic session is simpler, revokes instantly, and spares you from explaining why the user you just removed keeps getting in for thirteen more minutes.

## Three rules to remember

- **The server does not store the access token**, so it cannot deactivate it — it can only wait for it to expire. `expiresIn` is the size of that wait.
- **The real logout is the refresh token's.** Deleting its row cuts the session going forward; the live access token is the window you choose to live with.
- **The payload is a photo, not a mirror.** Anything you put in it stays true to the server until the token dies, even after it stopped being true in the database.

Open your API, copy a valid access token, log out, and repeat the request. If it returns 200, you now know exactly how many minutes that window lasts — and if it returns 401, go find the lookup that makes it possible and what it is costing you.
