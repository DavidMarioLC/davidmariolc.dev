Montando Velite en este sitio me encontré con algo que vale la pena anotar: por
defecto, un fallo de validación de esquema **no** rompe el build.

## Qué pasa

Quita un campo obligatorio de una pieza de contenido y compila. Velite imprime el
error, descarta el registro y sale con `0`:

```text
[VELITE] issues:
content/projects/en/sqm-nutrition.mdx
 error Required  title

✖ 1 error
[VELITE] build finished in 168ms
```

La palabra "finished" ahí está trabajando mucho. El proyecto desapareció de la
salida, el código de salida dice que todo está bien, y `velite && next build`
continúa tan tranquilo a construir un sitio al que le falta una página.

## Por qué importa

El modo de fallo es del tipo peligroso: **silencioso y parcial**. Un build que
revienta se arregla en minutos. Un build que tiene éxito mientras descarta uno de
cada veinte elementos se detecta semanas después, y lo detecta un visitante.

<Callout type="info" title="Una fuente, tres superficies">
  En este sitio [el listado](/posts), el sitemap y el feed RSS leen todos la misma
  colección. Es deliberado: un borrador desaparece de los tres a la vez, sin
  listas paralelas que se desincronicen. La contrapartida es que lo que se
  descarte al compilar desaparece también de los tres a la vez, y nada aguas
  abajo puede distinguir entre "sin publicar" y "perdido".
</Callout>

Además rompe una suposición fácil de hacer. Si el contenido es la fuente de verdad
del listado, del sitemap y del feed, entonces "el contenido compiló" tiene que
significar "compiló todo".

## El arreglo

[Velite](https://velite.js.org) acepta una opción `strict`. Ponla en el script, no en el config:

```json title="package.json"
{
  "scripts": {
    "build": "velite && next build" // [!code --]
    "build": "velite --strict && next build" // [!code ++]
  }
}
```

<Callout type="warning" title="El campo del config no es el flag">
  Poner `strict: true` dentro de `velite.config.ts` no me hizo efecto — el build
  seguía saliendo con `0` ante un archivo roto. Solo el flag de la CLI cambió el
  código de salida. Si lo configuras y sigues adelante, te queda el fallo
  silencioso que querías evitar, más la falsa confianza de haberlo resuelto.
</Callout>

Las tres formas de configurarlo, y lo que hace cada una de verdad:

| Ajuste | Dónde va | Código de salida | Registro inválido |
| :--- | :--- | :---: | :--- |
| nada | — | `0` | se descarta, el build sigue |
| `strict: true` | `velite.config.ts` | `0` | se descarta, el build sigue |
| `--strict` | el script `build` | `1` | el build se detiene |

Con `--strict`, el mismo archivo roto ahora sale con `1`:

```text
✖ 1 error
[VELITE] Schema validation failed.
```

## Prueba el modo de fallo

Lo importante no es el flag, es la forma del fallo. Aquí en miniatura: un
"pipeline" que descarta lo que no puede parsear y reporta éxito igualmente.
Cambia `parse` para que devuelva `null` ante una entrada mala y mira cómo el
resumen sigue diciendo que todo está bien.

<VanillaPlayground
  title="Fallo silencioso y parcial"
  html={`<pre id="out"></pre>`}
  css={`body { font: 13px ui-monospace, monospace; padding: 12px; margin: 0 }
#out { white-space: pre-wrap; line-height: 1.6 }`}
  js={`const input = ["2025-06-01", "not-a-date", "2026-02-01"];

// Descarta lo que no puede parsear y no dice nada.
function parse(value) {
  const date = new Date(value);
  return Number.isNaN(date.getTime()) ? null : date;
}

const parsed = input.map(parse).filter(Boolean);

document.getElementById("out").textContent = [
  "entrada: " + input.length + " registros",
  "salida:  " + parsed.length + " registros",
  "",
  "build finished ✔  (exit 0)",
].join("\\n");`}

## La parte que casi se me escapa

Probando esto encontré un segundo problema, más callado. Antes de seguir leyendo:
un post declara `date: not-a-date` en vez de una fecha ISO. Todos los demás
campos están bien. ¿Qué imprime el build?

<Challenge summary="Ver lo que imprimió">
  Tres palabras. Sin archivo, sin campo:

  ```text
  [VELITE] Invalid time value
  ```

  Ni `content/posts/es/loquesea.mdx`. Ni `date`. Solo el mensaje, y cien
  archivos que revisar a mano.
</Challenge>

La causa es que `s.isodate()` lanza un `RangeError` crudo en vez de añadir un
issue de esquema, así que se escapa del reporte de errores que sí nombra archivo
y campo para cualquier otro tipo de fallo. Haciendo la validación dentro del
transform se recupera:

```ts
const isoDate = s.string().transform((value, ctx) => {
  const parsed = new Date(value);

  if (Number.isNaN(parsed.getTime())) {
    ctx.addIssue({ code: "custom", message: "Expected an ISO date" });
    return z.NEVER;
  }

  return parsed.toISOString();
});
```

Ahora el error nombra las dos cosas:

```text
content/projects/en/sqm-nutrition.mdx
 info Expected an ISO date  date
```

<Callout type="tip" title="Compruébalo en dos minutos">
  Borra un campo obligatorio de una pieza de contenido y lanza tu build. Después
  mira el **código de salida**, no lo que imprime por pantalla:

  ```bash
  npx velite; echo "exit=$?"
  ```

  Si imprime `exit=0` mientras reporta un error — el caso de [qué
  pasa](#qué-pasa) — tu pipeline está descartando
  registros y tu proceso de despliegue no tiene forma de enterarse.
</Callout>
